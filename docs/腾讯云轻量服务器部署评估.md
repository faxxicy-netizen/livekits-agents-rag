## 结论

不建议原样部署本地全模型版本。当前剩余内存只有约 1.5 GiB，且没有可用的 NVIDIA GPU。现有实现会在 API 和语音工作进程分别加载 BGE/PyTorch，语音工作进程还要加载 SenseVoice、Kokoro 和 VAD；Linux 进程模型也需要纳入内存预算。默认 Kokoro 使用 CUDA，无 GPU 时会直接报错；改成 CPU 能消除该配置错误，但不能保证实时合成速度。

此结论依据现场资源和代码结构；没有在远端安装模型或进行推理、并发压测。

## 使用现有服务器的候选方案

保留前端、FastAPI、SQLite、少量知识库数据的 Qdrant、单实例 LiveKit 与语音 Agent，将 STT/TTS 改为外部接口，LLM 沿用 DeepSeek。embedding 改为较轻的 CPU/ONNX 实现，或接入外部 embedding 接口，减少重复加载。部署前仍需验证实际常驻内存、单路语音响应和网络连通性；不承诺 2 GB 已经足够。

另一种演示方式是让本地电脑继续处理模型，服务器提供公网入口和音频房间。这需要设计安全隧道及 API 路由，保持文档/会话数据来源一致，且演示时本地电脑必须在线，不能只把 Agent 的 LiveKit 地址改成云端就认为迁移完成。

## 公网版还需改动

- 将 Windows `.exe` 与 PowerShell 启动脚本替换为 Linux 二进制及受管理的服务。
- CPU-only 机器调整依赖选择；当前 uv 配置在 Linux 上也选择 CUDA 版 PyTorch，不宜原样安装。
- 将仅允许 localhost 的 Origin 检查改为明确的部署域名白名单，配置合适的绑定地址和浏览器使用的 LiveKit 公网地址。
- 配置 HTTPS/WSS、可信证书、LiveKit 公网地址与媒体端口；现有 HTTP localhost 的开发配置不能直接作为远程浏览器语音部署配置。
- 增加演示入口访问控制。当前知识库管理面向本地共享空间，没有真正的用户登录，公网开放前需要限制访问；Qdrant 和 Agent 健康端口保持内网访问。
- 模型文件在本机预下载后上传，或验证可靠的下载路径；不要依赖服务器首次启动时临时下载 Hugging Face 模型。
