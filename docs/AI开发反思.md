# AI 辅助开发反思

## 协作方式

项目使用 Codex 辅助需求拆解、官方文档查询、代码实现与问题定位。开发者负责功能方向、模型选型、部署约束，以及实际语音体验的判断。AI 参与了前后端、LiveKit 接入、RAG、测试与部署脚本的实现。

AI 生成的实现需要通过代码阅读、针对性测试和实际体验验证。本文记录主要取舍与经验；当前架构见 [项目架构与 RAG 链路](项目架构与RAG链路.md)。

## 主要设计取舍

1. **实时通信与业务逻辑分开。** LiveKit 负责音频、轮次和播放调度，自定义 `llm_node()` 负责检索与生成。通过节点扩展接入 RAG，无需修改 SDK 源码。
2. **模型服务独立配置。** 早期采用 SenseVoice 和 Kokoro 本地推理；服务器方案将 ASR、TTS、LLM、Embedding 放到云端，SQLite、Qdrant 和业务服务留在服务器。本地模型仍可选，避免小内存服务器常驻较重的模型。
3. **逐句生成与播报。** LLM 通过 SSE 返回带引用的短句，应用解析并校验后交给 LiveKit 合成播放，后续生成与前句播放重叠，减少等待全文完成的时间。
4. **知识库保持通用。** 检索使用用户原文，历史参与模型理解。每个知识库独立配置助手定位和回答方式，会话保存配置快照；不再按特定产品、型号或问句形式改写问题。
5. **资料与索引有明确的生效边界。** 文档通过上传接口管理，先写向量再发布正文版本，检索限定知识库和当前文档版本。删除自建知识库会清理文档、旧版本和向量，保留历史会话与引用供查看。
6. **按功能组织代码。** 将平铺模块拆为 `api`、`conversation`、`voice`、`knowledge`，让 `main.py` 只承担应用组装。配置、共享数据结构和会话存储暂时保留在顶层，控制拆分复杂度。

## 迭代中发现的问题

- **示例规则影响通用性。** 早期围绕路由器资料加入型号过滤、别名替换和追问补全，切换到 IoT 文档时会误伤召回。最终移除这些规则和专用 TTS 读法替换。代价是省略式追问可能召回不足，需要用户补充完整问题。
- **流式处理需要贯穿链路。** 即使 TTS 能流式返回音频，等待 LLM 完整生成仍会造成明显延迟。改为 LLM 流式输出、逐句解析与合成后，才消除了这部分整段等待。
- **结构化输出仍需校验。** 曾遇到普通文本输出、JSON 模式空白回复等问题。通过统一历史回答格式、限制输出协议并校验来源 ID 提高稳定性；引用合法并不能保证语义上完全正确。
- **打断后的数据要与实际播报一致。** 为轮次增加标记，取消旧生成、丢弃过期音频，并根据 SDK 保留的播报转写关联引用，避免未说完的内容被当作完整回答保存。
- **本地与浏览器环境存在兼容问题。** Windows 原生库加载、中文路径、Python 启动器子进程，以及浏览器 PeerConnection 配置都需要实际定位。解决方式限定在应用范围内，避免修改全局环境。
- **删除功能需要处理关联关系和并发。** 删除知识库不仅涉及列表，还涉及向量、文档版本、历史会话和进行中的任务。当前实现会阻止通话或回答期间删除，并拦截删除期间的新请求；向量清理失败时保留 SQLite 数据供重试。

## 验证范围与局限

最近一次功能验证通过 **91 项离线测试**，覆盖检索、知识库隔离、文档版本、引用校验、流式解析、打断生命周期、访问控制和删除并发。目录拆分前后的 OpenAPI 定义也做过一致性比较。

服务器实际验证了登录保护、临时文档上传、云端向量化、向量检索和知识库删除，并确认删除后没有该测试库的向量残留。临时数据已清理。语音链路此前验证过公网连接和欢迎语音频；最近的结构调整与删除功能没有重复执行完整的多轮语音端到端测试。

当前验证仍有边界：

- 历史固定题集规模较小，旧报告不能代表当前实现或其他主题文档的准确率。
- 真人口音、噪声、回声、音色和长时间使用体验，需要实际语音测试。
- 当前服务器按单路演示配置，未进行并发容量或长期稳定性压测。
- Dify 适配器保留，但业务入口禁用，尚未验证独立知识库映射。

## 开发经验

AI 能较快搭出跨组件的初稿，真正需要持续判断的是模块边界、异步取消、数据一致性和使用体验。后续迭代优先用小范围、可复现的检查验证变更；遇到新的框架行为、并发问题或实际体验差异，再补充对应验证，避免重复运行成本较高的完整流程。
